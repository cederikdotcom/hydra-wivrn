# Completeness critique of the #739 design field

Written by an adversarial reviewer against all four candidate designs, 2026-09-16.
Kept because several findings here are load-bearing and were verified afterwards.

## What the field missed

### 1. A modality nobody proposed: our own Meta app id and a private release channel

All four designs converge on the same pipe (CI signs an APK, hydrarelease hosts it, HMS installs from the URL) and treat adb as the lab lane. Nobody proposed the one channel that already has working code in the repo: `ovr-platform-util upload-quest-build --app-id <id> --token $OCULUS_TOKEN --channel $CHANNEL` at `/home/claude-user/hydra-wivrn/.github/workflows/Build.yml:317-334`. Every survey found it, and the only conclusion anyone drew was defensive ("never set OCULUS_TOKEN or we push to upstream's app id 7959676140827574"). Invert it. Create a Hydra Meta app id, set our own token, and push the `oculus` build type to a non-LIVE release channel. A release channel is an invite list of Meta accounts; builds installed from it arrive through the normal store UI with normal background auto-update, no developer mode, no unknown sources, no cable, no MDM, and no store review (review gates LIVE, not channels). That is the only proposed or unproposed path in this whole field that gives silent updates on a stock consumer Quest without an MDM, and it costs a Meta developer organisation, which #544 already says we need anyway. It also composes with HMS rather than competing: HMS for device policy, the channel for app delivery. The field spent four designs solving artifact hosting, which is the easy half, and left the one delivery mechanism with shipping code in the tree unexamined.

Three smaller modalities also went unconsidered. **Buying the arbitration instead of building it:** ManageXR and ArborXR are named in #544 as Meta-approved and were never priced or trialled, yet both ship per-device app version reporting and single-app kiosk pinning, which is precisely the head inventory field and the OpenXR arbitration that three designs propose to build into hydracluster and hydraheadquest. For a fleet of one Quest going to maybe five, "pay for it" deserved at least a rejected-option paragraph. **Serving the APK from the venue, not the internet:** see the 6 GHz island problem below. **Not distributing a second client at all:** the entire problem exists because PyroWave lives in WiVRn. Nobody asked what it would cost to carry the PyroWave codec in the client we already sign, distribute and version (hydraheadquest has its own OpenXR renderer at `app/src/main/jni/xr-renderer/xr_renderer.c`). That may well be too expensive, but "move the codec to the client" is the option that deletes the issue rather than solving it, and it was never on the table.

### 2. Claims everyone assumed

**HMS is load-bearing in all four designs and nobody has an account.** Every rollout parks HMS in a later phase while relying on it for the steady state. The estate has already run this exact play once: ABM is #518, still open a month later, blocked on external verification that "takes days". Meta's managed services require a verified business organisation on the same shape of paperwork. Nobody scheduled it, so the long pole with a multi-week external dependency is the one item with no owner and no start date.

**The kill shot nobody made a gate: the WireGuard tunnel under HMS.** The head reaches hydracluster only over the mesh, and the mesh tunnel exists because someone ran `adb appops set <pkg> ACTIVATE_VPN allow`. That pre-grant needs adb, which needs developer mode. If HMS enrolment excludes or resets developer mode (plausible for a managed provisioning mode), there is no way to grant `ACTIVATE_VPN` to an HMS-deployed app, the tunnel never comes up, the head never heartbeats, and every design collapses regardless of how well its APK is signed. The survey flagged this as "a risk to verify early" in one bullet and not one proposal made it a precondition. Relatedly, nobody asked whether HMS enrolment requires a factory reset of the existing Quest 2, which would destroy developer mode, both sideloaded apps and the pairing state on the only headset in the fleet.

**"Developer mode requires a Meta developer organisation."** This is sourced entirely to our own runbook written on 2026-08-21 and never re-verified, yet it is what disqualifies the lab lane and what makes the `fleet-ops` B0 lane look impossible. It is ten minutes with a phone and the headset to re-check.

**"Only one XR client can hold an OpenXR session at a time."** The brief asserts it as a fleet fact and every design builds on it, but the coexistence survey states plainly that no one has ever observed it. The distinction that matters is not "one session" but what the incumbent receives when a second immersive app launches. If Horizon OS sends `STOPPING` and backgrounds it, the handoff is free, both clients coexist happily, and the `one-app` design's entire reason for existing evaporates along with half of `fleet-ops`'s policy machinery. If it sends `EXITING`, WiVRn calls `exit(0)` and the designs are needed. This is a twenty minute experiment on hardware we already own, and it determines which design is correct. It should have been a gate in every proposal and was a gate in none.

**The release URL claim is wrong as published.** Two proposals claim to have verified the `latest` alias live and seen a 302 to hydramirror with a 200. I re-ran it today: `https://releases.experiencenet.com/hydrawivrn/production/latest/hydra-wivrn-server.pkg.tar.zst` returns **404**, because the only artifact ever published to that project embeds the version in its filename (`hydra-wivrn-server-0.0.0.pyrowave.r2795.abda7da8-1-x86_64.pkg.tar.zst`). The alias mechanism works (that full name through `/latest/` does 200 with 2,178,157 bytes) but the constant-filename convention every design depends on has never once been exercised in this estate. More interesting, the 302 target is `bxl1.hydramirror.experiencenet.com`, which resolves to 141.227.136.199, the same edge box as hydraissue. So the permanent MDM install URL every design hands to Meta actually dereferences to a single district-named host that also runs the issue tracker. Nobody asked what that hostname means for a venue outside bxl1, whether the redirect is chosen per client, or whether Meta's cloud fetching from a `bxl1.` host is what we want. It is one host away from "no headset, no body and no MDM can fetch anything".

### 3. Operational failures nobody designed for

**Quests sleep on the charger.** Horizon OS drops activity starts while asleep and background starts are SWMS-rejected; both facts are in the field's own evidence and both were used only to argue about launching the XR client. Neither was applied to updates. An overnight silent update assumes a device that is awake, on Wi-Fi and reachable, which a headset in a locker is not. The real update window is the ninety seconds after an operator picks it up and before a visitor puts it on, and no design has an interlock preventing a head from entering self-service while a 32 MB APK is landing.

**The 6 GHz island.** PyroWave mandates a dedicated 6 GHz AP with the headset as its only client. A Quest has one radio and one association. The live head record shows `wifi_ssid: Rotar`, `local_ip 192.168.68.50`, `wireguard up`, so today the headset reaches hydracluster over WireGuard over the venue SSID. Moving it to the dedicated AP moves the heartbeat, the command poll, the MDM check-in and every APK download onto that AP as well, and if that AP is an isolated segment (which is how most people build "dedicated AP, one client"), the headset is off the mesh for the entire session and cannot be updated on it at all. Nobody stated this, and it is the strongest argument for the LAN-served APK modality above: the body is on that same wired backhaul.

**There is no canary ring, and the mechanism is sitting unused.** hydrarelease has exactly two channels. Every design points the fleet at `production/latest`, which is one pointer for every headset, and every design correctly notes that rollback is impossible because Android refuses a versionCode downgrade. Combine those two and a bad client is a fleet-wide outage recoverable only by a fresh CI build. Assign the lab Quest to `staging` permanently and promote by hand. That is free and nobody proposed it.

**Nobody has ever restored the keystore backup.** Four designs discuss key custody and all copy the hydraheadquest pattern of a mode 600 master plus Storage Box u645590. For a secret whose loss forces a fleet reinstall, a backup that has never been restored is a claim, not a control. Restoring it into a scratch directory and checking that its signer SHA-256 matches the APK actually on the Quest costs fifteen minutes, and it simultaneously proves out the signer-SHA inventory idea that `fleet-ops` correctly identified as the best remote-verification trick available on a platform where `screencap` returns zero bytes.

**The debug-signed APK is worse than untidy.** One proposal wants the `pyrowave-test-1` prerelease deleted for hygiene. The actual reason is that a debug-signed APK is signed with the Android debug key, whose private half ships inside every SDK installation, so anyone who can reach that headset over adb can build something Android considers the same app and upgrade it in place, and the build is `debuggable`, which makes `run-as` work and the app's private data (including the PIN-derived pairing material in `common/secrets.cpp`) readable. The public 32 MB download advertises the target. That is a security finding, not a cleanup task.

**Our fork's CI already runs the full upstream matrix on every push.** I pulled the run list: the `pyrowave` branch push on 2026-09-14 ran Build, Format and Locales; the `master` sync ran Build for 51 minutes. That is real Actions spend on flatpak and Debian server legs we do not use, on every push, and it is the same matrix that would sign with a production key on every branch if anyone reused upstream's secret names. Incidentally it also resolves an "unknown" every survey listed as needing measurement: the **Android (Release) job takes about 6 minutes** (Debug 7, Oculus 9, DebugWithValidationLayer 9). Android build cost is a non-issue; the hour-long leg everyone would have seen in the wall-clock time is the flatpak server build.

**Licensing went entirely unmentioned by four designs.** WiVRn is GPLv3 (`COPYING`), and so is hydraheadquest (Moonlight lineage, `LICENSE.txt`), so the `one-app` absorption is compatible. But distributing a Hydra-branded binary obliges us to offer the corresponding source for that exact build to every recipient, which is satisfied only while the fork stays public. That becomes a live constraint the moment anyone proposes a private fork or a whitelabel build, and a whitelabel is already on the books under #672.

### 4. The framing is wrong

The issue is scoped as "WiVRn client distribution for headsets", but the target is Quest 3/3S and the fleet owns zero of them. The single Quest 2 is excluded by the codec ruling and has been `node_status: offline` since 2026-09-15. So every design is being validated on hardware where the payload cannot do its job, for hardware that has not been ordered, running a Horizon OS version nobody has specified (which matters: hydraheadquest declares `horizonos:uses-horizonos-sdk` 74/77 because v77+ refuses immersive frames without it, and the WiVRn manifest declares none at all, a fact that is untested precisely because our only device is on v76).

The honest question is not "how do we distribute the WiVRn client" but "how does this fleet install any app on a Quest without a cable", and the answer is identical for hydraheadquest, ALVR and WiVRn: it cannot, and the blocker is a Meta organisation nobody has started. Attaching that generic, externally gated capability to a codec experiment guarantees #739 cannot close until Meta paperwork clears. Split it. First, a device- and app-agnostic Quest fleet distribution issue whose first deliverable is a Meta organisation and one enrolled device, owned separately and started today. Second, a WiVRn client build and release issue (keystore, applicationId via `-Psuffix`, versionCode formula, publish to a new `hydrawivrnclient` project) that has no external dependency and could ship this week. Third, launch and arbitration in hydraheadquest, gated on the hardware experiment. Three of the four designs bundle all three and therefore have a rollout whose fourth step blocks on a business verification call.

One purchasing decision is time-critical and nobody raised it. Meta sells headsets through a business channel with the managed-services entitlement attached, and business-provisioned devices are enrolment-ready at first boot. If the Quest 3/3S are bought as consumer units, enrolment may require a wipe, exactly the trap #518 documents for the three iPads that "were NOT bought through Apple channels tied to us". The order has not been placed yet. Getting the SKU right is worth more than any of the four designs, and it expires the moment someone clicks buy.

### 5. The unknowns to resolve before committing, cheapest first

Run the coexistence experiment today on the Quest 2 with both APKs already installed: start an ALVR session, then `am start -a android.intent.action.VIEW -d "wivrn://<body>" -c com.oculus.intent.category.VR org.meumeu.wivrn.github.testing` through hydraadb, and read logcat for the `XR_SESSION_STATE_*` the incumbent receives. Twenty minutes, no money, and it decides which design is needed. Before that, spend one command checking whether the Quest still answers at 10.10.200.7:5555 through cluster exec on node-50ab5309, because every rollout in the field silently assumes it and `adb tcpip` does not survive a reboot. Re-verify the developer mode requirement with a phone and the headset, ten minutes, because it is the premise behind rejecting the lab lane. Read Meta's current managed services and release channel documentation to establish whether enrolment wipes a device, whether developer mode survives it, whether a `VpnService` app is permitted, and whether Meta's infrastructure or the device fetches the install URL, all of which are answerable from a browser today without an account. Start the Meta organisation application in parallel regardless, because it is the only item measured in weeks. Read the hydrabody side of the WiVRn D-Bus interface (`server/main.cpp:584-621`, `wivrn_server_set_pin`) to settle whether the cluster can mint the PIN that three designs need for a pairing-free `wivrn://:PIN@host` handoff, an hour with no hardware. And set `HYDRARELEASE_PUBLISH_TOKEN` on cederikdotcom/hydraheadquest and cut one `-rc` tag, which the whole field already agrees on and which nobody needs a chosen design to do.

Two "unknowns" can be struck off the list now: the Android build cost is about six minutes per leg on a hosted runner, and the release download lane works end to end from the public internet, with the caveat that the constant-filename convention every design assumes has never actually been used.
